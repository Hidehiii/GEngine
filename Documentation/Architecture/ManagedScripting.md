## 1. 目标与范围

开发机只准备一份版本固定的 Mono Runtime SDK，编辑器 Worker、示例和开发游戏
共享使用；重新编译 C# 只更新程序集，不向每个 EXE 目录复制 Mono。
导出独立游戏时，打包工具自动部署所需运行库；再次导出跳过内容未变化的文件。
独立包必须脱离开发机 SDK 和当前工作目录运行，不要求玩家另外安装 Mono。

以下为整体目标，具体已实现能力见顶部状态和第 7 节 S2.1。实施顺序为 S0 路径与初始化、
S1 SDK/程序集、S2 增量导出、S3 编辑器编译与 Worker 重启。
不在首版引入进程内热重载、现代 .NET 迁移、AOT、自动裁剪或完整托管组件系统。

| ScriptEngine.cpp | 使用 RuntimeSpecification 的 ScriptRuntimeRoot / ScriptCoreAssembly。 |

| RuntimeSpecification | 提供 EnableScripting、ScriptRuntimeRoot 与 ScriptCoreAssembly。 |

| Sandbox/部分 Example | 存在五份相同的旧 mono/lib/mono/4.5 副本；见下方审计。 |
| Qt EngineWorker | 当前关闭脚本；Host 不加载 Mono。 |

2026-10-26 S1.0 审计：Sandbox、DeferredRender、GpuDriven、InputSystem、
ShaderCompile 的 4.5 BCL 目录均为同一 445 文件副本，每份 80,109,965 字节；
mscorlib/System 的文件版本为 4.6.57.0。Debug/Release
libmono-static-sgen.lib 与公开 Hazel 仓库提交 b22a7550 的同名二进制完全
一致，静态库对象路径也指向 `C:\Dev\Hazel\2D\libs\mono\msvc`。本地 BCL
与 Hazel 当前 Hazelnut 副本不同，最早由本仓库 2024-07-23 提交 94835394
引入且无来源说明。官方 Mono 6.8.0.105、6.10.0.69、6.10.0.87 x64 MSI
的管理解包结果均不匹配本地静态库或 4.5 mscorlib。随附 LICENSE 与 Hazel
一致，主体为 MIT，另有 BSD/Apache/MPL/GPL-with-exception 等组件；其引用
的 PATENTS.TXT 未随快照提供。

静态链接原生 Mono 不等于已包含托管基础类库。mscorlib 等程序集仍需从匹配的
运行库目录加载。关闭脚本后可以省去托管运行库部署，但现有引擎仍链接原生
Mono；完全消除原生链接依赖不属于此次方案。

S0.1 已处理域/程序集检查、部分失败清理及托管异常接收；真实启用脚本的运行
与故障验证仍待补齐，不能从编译成功推断脚本运行已通过。

## 3. 依赖与所有权

- Qt Host 拥有文档、编译状态、Console 和所属 Worker，不加载托管程序集。
- EngineWorker/独立游戏拥有 Mono 域、托管对象与脚本执行；故障留在该进程内。
- 开发运行库 SDK 是只读共享输入，按 Runtime ID 隔离；项目构建不得改写它。
- ScriptCore、项目脚本与依赖程序集属于具体构建产物，按配置和 Build ID 隔离。
- 游戏导出器拥有其清单列出的部署文件，不拥有用户任意放入输出目录的文件。

脚本路径与打包不改变 OpenGL/Vulkan/D3D12 的接口或 GPU 所有权。三后端仍需
验证 Worker 在启用脚本后正常启动、渲染和关闭，不能从单一后端结果推断其他后端。

## 4. 一份经过验证的 Runtime SDK

建议开发布局（目标结构，当前未创建）：

```text
EngineSDK/
  ManagedRuntimes/<runtime-id>/
    runtime.json
    mono/lib/mono/4.5/mscorlib.dll
    mono/lib/mono/4.5/<approved-runtime-assemblies>
    mono/etc/<required-config>
    Licenses/
```

runtime.json 固定原生 Mono 来源/版本与内容摘要、架构、托管库 profile、各文件
哈希、配置、许可证以及已验证组合。Runtime ID 由经验证的组合产生，不能只用
“Mono”或“4.7.2”作为兼容性标识；项目目标框架不是运行库版本。

S1.0 审计已确认：当前静态库来自 Hazel 二进制快照，示例 BCL 无法追溯到
匹配官方包，且 LICENSE 不是完整再分发合规证明。S1 必须先选定可复现来源、
取得所需许可/专利文件并验证原生库与 BCL 配对。未经验证不得直接把某个
Example 的目录提升为正式 SDK；首次引入供应文件也不在文档轮实施。

首版采用经过验证的运行库文件集合，不做自动 tree-shaking。静态引用分析不能
证明反射、动态加载、配置选择和区域数据不需要某个文件。项目动态依赖应显式
登记；缺失依赖导致预检失败。只有经独立验证后才缩减分发集合。

## 5. 路径规则

启动方显式选择 Development 或 Packaged 模式，不能因查找失败偷偷切换模式。
路径解析在 Mono 初始化前完成，日志记录选中模式、Runtime ID 和最终路径。

| 模式 | 解析规则 |
| --- | --- |
| Development | 显式启动配置 → 项目本地启动清单 → 开发专用环境覆盖；均需匹配 Runtime ID。 |
| Packaged | 只读 EXE 旁的游戏清单，所有部署路径相对包根目录；不读取开发环境覆盖。 |
| Legacy | 如迁移需要，单独显式启用旧工作目录布局并记录弃用提示，不作隐式兜底。 |

显式配置有值但无效时立即报错，不回落到低优先级来源。开发启动清单的相对路径
以清单所在目录为基准，环境覆盖要求绝对路径；仓库不提交个人机器 SDK 绝对路径。
包根目录以可执行文件位置确定，与启动时 cwd 无关。拒绝包内路径穿越及通过链接
逃出包根的文件；脚本程序集路径与 Mono 基础库路径独立配置。

EnableScripting=false 时跳过路径查找、SDK 校验和域创建。显式请求脚本但缺失
运行库/程序集时返回可诊断失败，不能静默禁用脚本；Host 保留文档并允许重试。

## 6. C# 编译与加载

Premake/CMake 消费同一份脚本构建描述，输出 ScriptCore、项目程序集、符号和
依赖清单。首版保留当前目标框架，使用开发机编译工具；编译器不随游戏分发。
CMake 的 C# 构建接入属于 S1，不能把当前只有 C++ 的成功构建视为脚本已验证。

每次编译输出到独立 Build ID 目录；全部成功并校验后才切换“最近完整构建”指针。
Worker 不加载正在写入或只更新了一半的 DLL。编译失败保留上一份可运行产物，
错误关联项目、文件、行和列，汇入编辑器 Console。

初始化先预检运行库和程序集，再创建 root/app domain，逐步提交状态。任何阶段
失败释放已获得的资源，Shutdown 可处理未初始化与部分初始化；必要操作和错误
检查在 Release 同样执行。托管调用捕获异常并转成日志/会话失败，不继续调用空对象。

首版重载通过停止旧 Worker、等待其退出、启动新进程并加载完整构建完成。不得
依赖同一进程里反复 mono_jit_cleanup/init 实现热重载。Host 草稿/历史不受重启
影响；完整 Scene 快照、运行状态恢复与无缝热重载另行实施，不在当前原型中承诺。

## 7. 增量游戏导出

S2.4/S5.1 替换 S2.3：`.gproject` 仅保存名称/版本，没有任何打包字段。Qt 打包
仅选输出目录，Host 异步运行自动 Release 构建、.gpak 归档和目标根目录发布，
不加载引擎 DLL。原生入口校验/展开资源包，不需要玩家安装 PowerShell。
当前自动构建显式排除 Mono，脚本初始化请求明确失败；C# 支持保持开放。
GUI 只有输出路径输入，构建要求与格式见 [打包指南](../Guides/GameExport.md)。

2026-10-26 S2.1/S2.2 曾实现 `BuildScripts/ExportGame.ps1`（PowerShell 7.2+，
替换初版 Python 工具）；该目录部署原型已于 2026-10-27 移除，由原生
`.gproject`/`.gpak` 管线取代。历史设计基于显式文件 ID 和
依赖闭包预检，生成包含哈希/大小/角色的版本化部署清单；新增/变更文件复制到
隔离 staging，未变文件仅从已发布版本硬链接，校验后发布内容寻址版本，再
原子替换 current 指针。源构建文件绝不硬链接；已发布文件必须不可变，游戏
缓存/存档/可写配置须另存。重复导出不复制 payload，也不重写指针。
历史版本与用户文件保留，不自动清理；独占 lock 拒绝并发导出。失败保留旧指针，
指针发布失败可能留下完整但未引用版本，重试可复用。工具仅面向可信目录，
不防范外部进程竞态修改文件系统。

该子项要求关闭脚本，不自动扫描原生/资源引用、不改写资产路径，也未接入
引擎启动清单。它不等同于完成 S2/S4 或已经能运行的独立游戏包。
[真实命令、输入与恢复边界](../Guides/GameExport.md)。GPU/后端公共接口、
资源所有权和现有构建流程均不变。

S2.2 的 FrameGraphTriangle 适配器收集现有构建 EXE/DLL、配置、shader 和独立
启动脚本；不推断通用原生/场景依赖。引擎退出会序列化 Config.ini，因此启动器
先验证整个发布版本，再把资源和配置复制到独立用户会话目录，EXE/DLL 仍从
发布版本加载，日志/缓存/配置变动留在会话目录。子进程 PATH 仅含包与系统目录，
清除开发 GENGINE/VK/MONO 覆盖，调用 cwd 不影响运行。首版每次使用新会话，
不承诺设置/缓存跨会话保留。此边界不修改 C++ 运行时或 GPU 接口。
已有 Release 示例二进制的三后端部署运行结果记录于 TODO；不等于重新构建了
当前引擎源码，也不能证明干净机器、完整场景或脚本游戏已验证。

目标目录：

```text
Game/
  Game.exe
  GEngine.dll
  game-runtime.json
  Runtime/Mono/<validated-runtime-files-and-licenses>
  Scripts/GEngine-ScriptCore.dll
  Scripts/GameScripts.dll
  Assets/
```

开发输出不复制 Mono。导出是独立操作，不能挂到每次 C++/C# 编译后的无条件复制。
导出流程：读取构建/运行库清单 → 预检完整依赖 → 计算部署计划 → 写隔离 staging
→ 验证哈希/路径/启动依赖 → 发布版本目录并切换当前版本指针。

以文件内容哈希而非时间戳决定复制。计划输出新增、更新、复用、删除数量及字节数；
内容不变时目标文件不重写，第二次无变化导出必须零复制。staging 可复用匹配哈希
的已有文件；不以硬链接共享可能被后续构建原地改写的脚本文件。

清理只针对上一份有效导出清单拥有的文件；拒绝 SDK/source/output 路径重叠。
不递归清空任意用户目录，也不覆盖正在运行的游戏文件。首版导出至受管理版本目录，
失败保留旧版本；切换指针文件使用原子替换，不宣称任意 Windows 目录替换都原子。
清单不携带开发机器绝对路径。分发目录可以改名、搬移或由任意 cwd 启动。

### 7.1 资源收集与目录部署（首版范围）

游戏导出同时包含运行所需资源，不仅是 EXE、Mono 和脚本 DLL。资源类别包括
场景、模型/网格、纹理、材质、着色器、音频及其他项目实际使用且受支持的资产；
某类资源的解析/运行时支持尚缺时，导出器应明确报错，不能宣称已经完整支持。

以启动场景及显式根资源为入口，递归收集依赖闭包，例如场景 → 材质 → 纹理/
着色器。按资源身份去重，检测引用环并终止遍历；不能因目录未被直接引用就
遗漏通过代码、反射、字符串路径或配置动态加载的内容。这些动态根与依赖由
项目显式声明，未知依赖不能靠静态扫描猜测。

同一资源清单记录稳定逻辑身份、类型、包内路径、依赖及内容哈希。当前仓库尚无
统一持久资源 ID 契约，首版可由导出清单分配/保存映射；不能把临时 UUID 当作
已实现的资产数据库。原始文件中的路径引用必须可解析到包内映射，必要转换由
明确的导入/导出适配器完成，不能只复制文件却留下开发机绝对路径。

首版将资源部署到 Assets/，沿用第 7 节的增量、staging、清理和发布规则。
缺失引用、身份/路径冲突、大小写规范化冲突及包外依赖都在发布前失败；不得
静默丢弃。修改一个资源只更新该资源及确实受影响的派生产物/清单，不复制未变
资源。首版不自动承诺纹理压缩、模型烘焙或跨平台 shader 编译；若产物依赖平台/
后端，构建清单必须区分目标变体，禁止复用不兼容缓存。

S4 是 S2 首版导出的资源工作流，不意味着资源部署推迟到游戏包完成之后。
验收必须在脱离项目源码和编辑器缓存的目录，加载启动场景及其完整资源集合。

### 7.2 资源归档（S5.1 最小原生格式已实现，其余仍为后续）

当前 .gpak 使用 GEPAK001 魔数、条目数、UTF-8 相对路径、大小与 SHA-256，
将资源流合并为一个未压缩/未加密文件。原生入口展开再走既有文件路径读取，
不冒充资产数据库或直接归档流式读取；各格式转换、压缩、随机访问和资源
读取适配仍未实现。下文为完整长期目标，不能覆盖已实现的最小归档事实。

资源归档是将资源合并为 .pak，并增加版本化索引、压缩与运行时读取适配；
它不同于最初的目录部署。S5.1 已提供上文最小写入/原生展开格式；下述统一
索引、压缩和直接读取方案仍为后续，不应把它们误记成已实现。

目录资源与 .pak 共用同一逻辑资源身份和依赖清单。未来的资源读取适配层屏蔽
文件目录与归档条目差异，场景和材质不直接保存 .pak 内偏移；当前代码若直接
读文件路径，必须显式迁移这些读取点，不能只更换扩展名。

S5 再设计索引字段、压缩策略、完整性/版本检查以及解压缓冲区和读取句柄的
所有权。目录与归档模式需加载等价内容，损坏/截断/缺项要可诊断，异步加载时
资源数据必须活到消费完成。归档内容更新可能重写整个归档，不承诺文件粒度
增量部署自动变为块级补丁；加密、防篡改、流式加载和补丁包均不在首版范围。

## 8. 验收与剩余工作

| 检查 | 验收结果 |
| --- | --- |
| 两个开发项目 | 共用一个 Runtime SDK，构建输出无 Mono 副本。 |
| 改动一份 C# | 只更新对应程序集/符号/清单，运行库不复制。 |
| 完整导出与重复导出 | 首次包含必要依赖和许可证；第二次零复制、文件时间不变。 |
| 修改一个依赖 | 只更新受影响文件，旧清单文件清理不影响用户文件。 |
| 资源闭包 | 启动场景与显式动态根的依赖全部可加载，无源码目录或包外路径依赖。 |
| 单资源更新与无效引用 | 跳过不变资源；缺失/冲突/不支持的资源类型导致发布前失败。 |
| 后续 .pak | 与目录模式资源身份/加载结果等价；损坏和不支持版本明确失败。 |
| 干净机器/隔离环境 | 无开发 SDK、无开发环境覆盖、任意 cwd 可运行。 |
| SDK/程序集缺失或损坏 | 预检明确失败，原游戏包与 Host 文档保持可用。 |
| 脚本编译/加载/托管异常 | Console 可定位，保留最近完整构建，可重启 Worker。 |
| 重复启动/停止 | 无残留子进程/域资源，记录内存行为与正常关闭证据。 |
| Debug/Release、三图形后端 | 分别记录脚本执行、渲染、故障恢复，未测组合明确标注。 |
| 关闭脚本 | 不查找或部署托管运行库，保持无脚本应用启动能力。 |

以上为完整里程碑验收，并非全部已通过。S2.1 的隔离部署回归不替代真实游戏
或脚本运行验收；S0/S1、运行时清单接入和资源格式适配仍由 TODO 跟踪。
